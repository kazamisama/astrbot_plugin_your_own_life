# 开发与发布工作流

## 总原则

- 每个会话先读仓库根 `AGENTS.md`（agent 自动加载）与 `docs/README.md` 文档顺序；新文件写入后从下一个会话起生效。
- 改动任何插件前，先读该插件源码（入口、核心模块、适配器、公开 API、测试），不读不改。
- 所有改动按“小阶段 / 单个功能”推进，不攒大包。
- 每阶段/功能落地：版本号 + CHANGELOG + commit + push 到对应 git 仓库。
- 推送前 review + debug + 测试；修复后再推一遍，保证远端是验证过的状态。
- 开发中主动联网调研相关项目/经验/论文，结论带来源记录；每个工作段落盘写开发日志（`docs/devlog.md`），保证上下文压缩后不丢信息、不偏航。

## 一、改动前：先读源码

- 读对应插件入口（`main.py` / Star）、核心模块、适配层、`metadata.yaml`、`_conf_schema.json` 与测试。
- 跨插件改动先看对方 `_PUBLIC_API.md` 或适配器实现，确认调用链（调用方 / 被调用方 / 依赖关系）。
- 确认不破坏 kazamisama 家族兼容（见 `docs/requirements.md` 生态兼容性约束）。

## 调研与开发日志（贯穿全程）

- 外部调研：开发前/开发中联网搜索相关项目、实现经验与论文（个人 Agent、记忆系统、RAG/召回、情绪/精力模型、AstrBot 插件生态等）；结论必须带来源（URL/仓库/论文标题），标注“已验证/推测/待验证”，没读过的资料不当事实。
- 调研产出：把值得借鉴的机制、可用依赖、踩坑点写进开发日志，注明采纳与否及理由。
- 开发日志：每个工作段结束（或上下文可能压缩/跨会话前）更新 `docs/devlog.md`，记录：目标、已确认决策、改动文件与函数、关键命令与测试结果、已验证/未验证项、遗留问题、下一步行动。
- 续接规则：新会话/上下文压缩后先读 `docs/devlog.md` 最新条目与 `git status` 再动手；日志随改动一起提交。
- 不丢失信息：决策、接口契约、版本同步点、待办与 blocker 必须写日志，不允许只存在于对话里。

## 二、小阶段推进

- 一个阶段 = 一个可交付功能或修复；小步提交，不混合无关改动。
- 版本同步点：`metadata.yaml` 与代码内 `__version__`（如有）。
- `CHANGELOG.md` 按 Keep a Changelog 写 Fixed / Added / Changed / Notes。

## 三、落地后验证

- 跑该插件测试（单测 + 可用的冒烟/集成，如 astrbot-test-kit）。
- review diff：最小修改、无无关文件。
- debug：复现、修根因、补测试。
- 修复后重跑全量测试。

## 四、推送

- 每个插件独立 git 仓库，origin 指向 kazamisama 对应仓库。
- 提交信息按仓库习惯：纯文档改动用 `docs: ...` 且不 bump 版本；功能/修复用 `chore(release): vX.Y.Z ...` 并同步版本与 CHANGELOG。
- review / debug / 测试通过后再 push；有修复先更新 CHANGELOG 与版本，再重新 push。
- 跨插件改动：上游先发兼容版本，下游再升级，整族协调。

## 五、安全边界

- 尽量不改不删工作区以外或未纳入 git 仓库的文件/目录；只操作当前插件仓库内的文件。
- 只读可以，修改/删除不行；确需改动先说明影响并确认目标属于工作区仓库。
- 缺依赖可以安装（`pip install` / `npm install` 等），按需安装、不扩散，不提交除必要锁文件外的多余变更。
- 临时文件清理前先校验路径（如 `$env:TEMP` 下自己创建的目录/文件），禁止对未验证路径做递归删除。

## Subagent 使用约束

允许使用 subagent 辅助调研、测试、审查与起草，但必须严格约束：

- 职责边界：subagent 只做调研/测试/审查/起草；决策、编辑、提交、推送由主 agent 完成。subagent 未获明确授权不得修改任何文件。
- 任务封装：每个 subagent 任务必须给出明确目标、必要上下文、输出格式与验收标准；上下文不足时先补齐，不让 subagent 猜。
- 事实纪律：subagent 结论必须区分“已验证/推测/待验证”，带来源（文件路径/行号/URL/测试输出）；禁止虚构日志、接口、测试结果。
- 权限边界：subagent 不得删除/移动/覆盖文件，不得执行 `git reset`、force push、批量替换；只允许读取与运行非破坏性验证命令。
- 落地闸门：subagent 输出必须先回主 agent review；符合验收才落地，落地仍走“小阶段 + 测试 + 推送”流程。
- 记录：subagent 任务、结论与采纳情况写进 `docs/devlog.md`，保证上下文压缩后不丢。
- 安全边界：subagent 同样遵守“不改不删工作区外或无 git 仓库内容；缺依赖可装”的约束。

## 测试清单

- 单测必须全绿；网络冒烟按插件配置执行。
- 跨插件改动跑上游 + 下游适配层两端测试。
- WebUI / 命令等真实运行路径尽量用 astrbot-test-kit 实测。

## Windows PowerShell 5.1 中文处理

- PS 5.1 通过管道把中文喂给 `python -`（stdin）会变成 `?`；不要用含中文的内联 Python/命令直接管道给解释器，改用 UTF-8 临时文件或 `apply_patch`。
- 写中文文档/代码优先用 `apply_patch`（UTF-8 安全）；写完后用 Python 以 `utf-8` 读回校验 `\ufffd` 与乱码。
- `safe_edit` 在 PS 5.1 下直接传中文 `--old/--new` 参数可能被破坏：用 `$env:SE_OLD / $env:SE_NEW` + `--old-env / --new-env`。
- PS 5.1 控制台按本地代码页显示 UTF-8 文件会出现乱码，不代表文件损坏；以 Python `utf-8` 读回为准。
- 内联 Python 校验脚本里的中文常量也可能被管道破坏导致误判；校验时用 ASCII 锚点或直接打印文件内容。
